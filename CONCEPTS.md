## 1. Что такое pi-board и её философия

**Суть.** Минимальная веб-борда над headless-режимом CLI-агента pi: слева — дерево
сессий (машина → рабочая папка → сессия), справа — чат, как в консоли. Каждое
сообщение пользователя = **один запуск** `pi -p --mode json --session <файл>` в
рабочей папке сессии: у каждой сессии свой полноценный контекст агента (инструменты,
правила, память). Ответ стримится в UI по SSE.

**Философия (в порядке значимости):**

1. **Файлы — истина, процессы — одноразовый транспорт.** Всё состояние ходов,
   реестров, досок — в файлах на диске. Смерть борды, ssh-канала или канала
   наблюдения ничего не теряет: после восстановления всё переподключается
   (ledger-модель, раздел 4).
2. **Zero dependencies.** Только стандартная библиотека Node (>= 18) и системные
   `ssh/git/tail`. Никакого npm-окружения для самого сервера. Это делает борду
   переносимой и самодостаточной.
3. **Борда — тонкий оркестратор, агент — исполнитель.** Борда не знает, что такое
   «код», «тесты» или «фикс»: она запускает агентов в папках, наблюдает стрим,
   раздаёт файлы и считает токены. Знания о проекте едут внутри репозиториев
   (AGENTS.md, скиллы) — борда агностична.
4. **Dogfooding.** Борда — обычное приложение, над которым работают её же сессии:
   сессия правит код борды, борда сама применяет ветку и перезапускается
   (self-reload, раздел 15), падение фиксит авто-откат и шлёт отчёт сессии-виновнику.
5. **Кооперативность вместо блокировок.** Там, где нет примитива синхронизации
   (общий файл с консолью, git-операции), — протоколы вежливости: «тишина файла
   15 с», «git-операции одного репо сериализуются (409)».
6. **Отказ вспомогательных механизмов никогда не ломает ход.** Память, библиотека уроков,
   коллаб-хинт — всё инъекции «поверх»: любой сбой тихо пропускается, ход идёт.
7. **Человек в цикле знаний.** Ничего не сохраняется в базу уроков без правки
   человеком; заметки памяти пишет только по явной просьбе; judge в экспериментах
   — человек.

**Слойность проекта:**

```
UI (public/*.html, vanilla)          ← SSE-клиенты, три вкладки: /, /board, /knowledge
HTTP-сервер (server.js)              ← роутер, SSE-хаб, ledger-раннер, ssh, git, reload
модули (compat/library/memory/refine/collab.js) ← installXxxRoutes(ctx), см. §3.4
исполнение (run.sh)                  ← лаунчер хода на машине исполнения
супервизор (scripts/serve.sh)        ← рестарт-цикл + авто-откат (rollback.js)
агент pi                             ← внешняя зависимость, контракт в §2
```

## 2. Контракт с агентом pi (внешняя зависимость)

Борда стоит на CLI-агенте pi. Если на целевой машине другой агент — эти точки
контакта нужно замапить на его возможности.

### 2.1 Headless-запуск

```
pi --mode json -p --session <файл.jsonl>   # один ход; stdout = поток JSON-событий
   [--append-system-prompt <текст|путь>]   # дописать в ХВОСТ системного промпта
   [--skill <путь>]…                       # подключить скиллы (дискавери из cwd)
   [--tools <allowlist>]                   # например "read,bash,edit"
   [--model <provider/model[:thinking]>]
   [--no-extensions]                       # выключить расширения (для -p-режима)
   -- <текст сообщения>                    # сообщение пользователя после --
```

Ключевые свойства: `--session` доопределяет файл контекста (ходы одного sid
продолжают одну историю агента); `--append-system-prompt` **дописывает в конец**
системного промпта — кэш промпта не инвалидируется (это критично для инъекций
борды); stdin игнорируется (иначе pi ждёт EOF и висит).

Служебные безсессионные вызовы (автоназвание, extract, proposer) идут как
`pi -p --mode json --no-extensions --no-session [--append-system-prompt sys] -- <prompt>`
— из ответа берётся последний `message_end` ассистента.

### 2.2 Поток событий (stdout, `--mode json`)

JSON-строки, по одной на строку. Используемые бордой:

| Событие | Что несёт | Зачем борде |
|---|---|---|
| `message_update` → `assistantMessageEvent.type` = `text_delta` / `thinking_delta` (`delta`) | стрим текста/мышления | live-чат |
| `…thinking_end` (`content`) | полный текст мышления | сворачиваемый чип 💭 |
| `…toolcall_start/delta/end` (`id`, `toolName`, `delta`, `toolCall`) | вызовы инструментов | чипы ⚡ с аргументами |
| `message_end` → `message` (role/content/**stopReason**/usage) | финальные записи | история + диагностика |
| role=`toolResult` (`toolCallId`, `toolName`, `isError`, content) | результаты инструментов | чипы ✓/✗ |
| `auto_retry_start/end` (`success`, `finalError`) | автоповторы модели | diag: «ретраил ×2» |
| `compaction_start/end` (`reason`, `result.tokensBefore/estimatedTokensAfter/usage`, `errorMessage`) | компакция контекста | diag + usage |
| `agent_settled` (`aborted`) | итог хода | diag |
| `tool_execution_start/end` c `toolName:"subagent"` (args, result) | запуск/_receipt сабагентов | карточки ▸ в чате |

`stopReason` значения: `stop` (норма), `length` (обрезан лимитом вывода), `error`,
`aborted`. `usage` = `{totalTokens, cost:{total}}`.

### 2.3 Формат файла сессии (`<sid>.jsonl`)

- первая строка: `{"type":"session","cwd":"…"}`;
- далее `{"type":"message","message":{role, content, …}}`:
  - `user`: content — строка или массив `{type:'text',text}`;
  - `assistant`: content — массив `{type:'text'|'thinking'|'toolCall', …}` + `usage`, `stopReason`;
  - `toolResult`: `toolName`, `isError`, content.

Парсер борды (parseHistoryText) превращает это в плоский список
`{role:'user'|'assistant'|'tool_result', …}` для UI и транскриптов. Формат один и
тот же для сессий борды и консольных сессий pi (`~/.pi/agent/sessions/<encoded-cwd>/*.jsonl`) —
на этом стоит раздел 16.

### 2.4 Прочее

`pi --list-models` — таблица моделей подключённых провайдеров (парсится колонками:
provider, model, context, maxOut, thinking, images; первая строка — заголовок);
дефолтная модель — из `~/.pi/agent/settings.json` (`defaultProvider/defaultModel`).
Конфиг pi: `~/.pi/agent/{auth,settings,models}.json` — его борда синкает на
ssh-клиенты (§6). Расширения (в т.ч. пакет `pi-subagents`, инструмент `subagent`)
включены в ходах по умолчанию; headless-падающие расширения исключаются в settings.

## 3. Модель данных и общие механики

### 3.1 Идентификаторы и время

Все id — 8 hex (`crypto.randomUUID().slice(0,8)` или `randomBytes(4).hex`):
id сессии (sid), задачи, форума, машины, репо, группы refine. Время — epoch ms.
Человекочитаемые номера (`n`) монотонно растут от собственного счётчика хранилища
и фиксируются при создании.

### 3.2 Реестры (JSON на диске, память процесса — кэш)

- **`data/registry.json`** — массив сессий. Поля:
  `{id, title, dir, host(null|hostId), repo(null|name), ref, model(null|id),
  ext(bool, расширения вкл по умолчанию), extFile(null|путь общего файла),
  createdAt, lastActivity, active(bool — ход идёт), preview(≤90 симв),
  archived(bool), truncated(bool последнего хода), usage:{tokens,cost,turns},
  diag:{stopReason,retries,compacted,loop,at}, lastTurnEnd:{at,state:done|stopped|error,seen}}`.
  runtime-поля (SSE-синк `_sink`) на диск не пишутся.
- **`data/hosts.json`** — машины: `{id, name, addr("user@host"), port(null|int), created, check:{ok,hasNode,hasGit,hasPi,version,error,at}}`.
- **`data/repos.json`** — репозитории: `{id, name(slug), origin(путь|URL), defaultBranch, created, lastSync, sync:{ok,at,error}}`.
- **`data/board.json` / `data/forum.json`** — коллаб (§9).

Правила: чтение при старте, запись после каждой мутации; невалидные записи
(без id) тихо отфильтровываются; `active` в registry — единственный флаг,
восстанавливаемый сверкой с pidfile (§4.6).

### 3.3 atomicWrite

Любое хранилище, которое читают другие процессы/машины (board.json, forum.json,
планы, meta.json), пишется так: tmp-файл (pid+3 hex) → `rename`. Читатель никогда
не видит половину файла. Внутренние реестры (registry/hosts/repos) пишутся
простой записью — их читает один процесс.

### 3.4 Паттерн модулей: `installXxxRoutes(ctx)`

HTTP-логика вне ядра живёт в модулях (library, refine, collab, memory, compat).
Модуль экспортирует `installXxxRoutes(ctx)` и возвращает async-handler
`(req,res,url) => bool` («true = обработано, стоп роутинга»); ctx — общий набор
хелперов сервера (`json, readJson/readBody, byId, broadcast, piOneShot,
renderTranscript, sshRun, hostById, running, startTurnEx…`). Это делает server.js
композицией, а модули — тестируемыми и переносимыми.

### 3.5 Env хода (turnEnv)

Каждому запуску хода передаётся окружение:
`PI_BOARD_DIR=<data-каталог машины исполнения>`, `PI_BOARD_PI=<бинарь>`,
`PI_BOARD_EXTENSIONS=1` (маркер «это ход борды» — расширение board-parity по нему
не дублирует инъекции, §16), и для ext-ходов — `PI_SUBAGENT_MAX_SPAWNS_PER_SESSION=12`
(кап сабагентов; в не-ext ходах переменную наоборот **снимают**, чтобы
унаследованное от окружения значение не протекало).

## 4. Ledger-исполнение ходов — центральная идея

**Ход = detached-процесс на машине исполнения + файловый протокол наблюдения.**
Транспорт (процесс борды, ssh-сессия, канал tail) одноразовый: всё, что нужно,
чтобы узнать состояние хода, лежит в файлах.

### 4.1 Артефакты

Локально — в `data/`, на ssh-клиенте — в `~/.pi-board/`:

```
<PI_BOARD_DIR>/
├── sessions/<sid>.jsonl   сессия pi (транскрипт; для extFile-сессий — путь переопределён)
├── journal/<sid>.jsonl    stdout pi (стрим событий) + сентинел {"board_exit":N} в конце
├── journal/<sid>.err      stderr pi (диагностика упавших ходов)
├── pid/<sid>.pid          pid процесса pi на время хода (наличие = ход жив)
```

Контракт простых sentinel-строк в журнале:
- `{"board_exit":N}` — ход завершён с кодом N (0 — успех; **130/143** — SIGINT/SIGTERM,
  т.е. ход остановили — это не ошибка; иное — ошибка, к ней прикладывается хвост stderr);
- `{"board_error":"cd_failed"|"pi_not_found"}` — лаунчер не смог стартовать.

### 4.2 Лаунчер run.sh (единый для локальной и удалённой машины)

```
run.sh <sid> <dir> <text> <noext:0|1> [append-system-prompt] [skills,через запятую] [tools] [model] [sessfile]
```

Шаги: создать артефакты (`: >> journal` — файл существует с первого мгновения,
иначе наблюдатель умрёт на «no such file» до переподключения и потеряет события);
`cd $dir` (провал → `board_error:cd_failed`); найти pi (`$PI_BOARD_PI` → PATH +
`~/.local/node/bin` — бутстрап на клиентах; провал → `board_error:pi_not_found`);
собрать argv (пустые опции **не попадают в argv** — позиционный контракт); запустить
pi в фоне `>> journal 2>> err`; `echo $pid > pidfile`; `wait`; `rm pidfile`;
`echo {"board_exit":$code} >> journal`. Деплой на клиент: борда копирует свой
run.sh в `~/.pi-board/run.sh` (один раз за жизнь процесса, shq-экранирование).

### 4.3 Запуск хода (startTurnEx)

1. Собрать инъекции (§4.4) → `append`.
2. Автоназвание сессии: один фоновый безсессионный pi-вызов по тексту сообщения
   («ответь ТОЛЬКО названием 2–6 слов»); фейл молча оставляет плейсхолдер.
3. Память recall (§11) — при включении, до запуска; отчёт вклеивается в текст хода.
4. Отметить в registry (`active:true`, preview, сброс truncated/lastTurnEnd), broadcast
   `status:running` + `user`.
5. Локально: detached spawn `/bin/sh run.sh …` с `stdio:'ignore'`, `detached:true`,
   `unref()` — pi переживает смерть борды. offset наблюдения = текущий размер журнала
   (граница хода: всё после — события этого хода).
   Удалённо: `PI_SUBAGENT_…=N nohup sh ~/.pi-board/run.sh <…9 аргументов shq-экранированы>
   </dev/null >>~/.pi-board/launch.log 2>&1 &` одним одноразовым ssh.

### 4.4 Инъекции хода

`--append-system-prompt` = склейка через `\n\n` (позже — `\n\n---\n\n` для дельты
варианта refine):

1. **Блок библиотеки уроков** домена (§10), cap 8000 символов.
2. **Коллаб-хинт** `<collab>…</collab>` (§9.5) — правило координации, curl-примеры
   с готовым author=sid, живое состояние доски. Удалённым сессиям адрес борды
   даётся только если она слушает не-loopback (`HOST=0.0.0.0`), иначе хинт не
   инъецируется.
3. **Сабагент-гайд** `<subagents>…</subagents>` — только для ext-ходов (§13).

Отладка: `PI_BOARD_DEBUG_LIBRARY=1` пишет весь блок в stderr борды.

### 4.5 Наблюдение: tail по byte-offset с переподключением

`tail -c +<off+1> -f journal/<sid>.jsonl` — локально процессом, на клиенте — тем же
`tail` поверх ssh. Читатель: копит буфер, режет по `\n`, **off += длина строки+1**
(байты, не символы!), на каждый живой чанк сбрасывает backoff. Потеря канала
(error/close) → reconnect-план: backoff 1с → 15с экспоненциально; перед ретраем —
`pidAlive` (локально `kill(pid,0)`, на клиенте `kill -0` по ssh): мёртв →
**resolveDeadTurn**: читаем последнюю строку журнала напрямую — есть сентинел →
финализация по коду; нет → ход завершается со статусом «unknown: process gone
without exit marker». `journalSize` на клиенте — `wc -c` по ssh; «-1» = клиент
недоступен (пробуем дальше).

### 4.6 Стоп, завершение, recovery

- **Стоп** (кнопка ■): SIGTERM процессу pi по pidfile (локально `process.kill`,
  удалённо ssh `kill` + fallback `pkill -f '<путь сессии>.jsonl'`), diag.stopped=true,
  финализация немедленно; поздний сентинел игнорируется (running уже пуст).
- **Завершение** (сентинел): код 0/130/143 → успешный финал; иначе — ошибка с хвостом
  `journal/<sid>.err` (6 строк).
- **Рестарт борды**: ходы НЕ убиваются. При старте все сессии с `active:true`
  сверяются с pidfile: живые — переподключаются к **текущему концу** журнала
  (завершившиеся между смертью и подъёмом сообщения читаются из файла сессии при
  открытии — ничего не теряется и не дублируется), мёртвые — `active:false`.
- **Транскрипт** живёт на машине исполнения; борда читает его `ssh cat` при надобности.

**Инварианты ledger:** (1) наличие pidfile ⇔ ход жив; (2) сентинел в журнале ⇔ ход
завершён и как; (3) наблюдение можно убить и пересоздать в любой момент без потерь
(буферизация не в канале, а в файле); (4) run.sh не зависит от жизни борды и ssh.

## 5. HTTP-сервер, SSE и события

Один `http.createServer`, большой if-роутер (не фреймворк). Роутер делится на:
static (`/`, `/board`, `/knowledge`, `/md.js`, `/ui/*` — вендорный UI), SSE
(`/api/events`), мета (`/api/meta`, `/api/health`, `/api/models`), fs (листинг
папок локально/ssh: `GET /api/fs?dir&host`, mkdir/rename/rmdir), hosts, repos,
library, refine, collab, memory, pi-sessions (консольные), sessions.

### 5.1 SSE-хаб

`GET /api/events` → `text/event-stream`, `retry: 2000`, heartbeat каждые 25 c
(`: hb`). `broadcast(obj)` пишет `data: <json>` всем клиентам. Все события имеют
поле `t` (тип); события сессии — `sid`. Отдельный SSE для coddy-событий (§18).

### 5.2 Протокол событий сессии (в порядке хода)

`status {status:'running'}` → `user {text}` → [`memory {phase}` §11] →
`thinking_delta`/`thinking_end` → `delta {delta}` (текст) → `tool_call {id,name}` →
`tool_args {id,delta}` → `tool_end {id,args}` → [`subagent {phase:'start',agent,task,async}` /
`subagent {phase:'done',runId}`] → `tool_result {id,name,summary,isError}` →
`assistant {parts,usage}` → `done {error?,notice?,truncated?,end,usage,stopReason,…}`.

Глобальные: `title {sid,title}`, `hosts_changed`, `repos_changed`, `lesson`,
`library_changed`, `board_changed`, `forum_changed {topic}`, `plan_changed {path}`,
`reload {reason}`, `seen {sid}`. Чужая `status/done/seen` → клиент просто обновляет сайдбар.

### 5.3 Seen-семантика (маркер внимания)

Индикатор «ход завершён» в сайдбаре должен **гаснуть**: `lastTurnEnd.seen=false`
при финале хода; `POST /api/sessions/:id/seen` гасит (открытие сессии или просмотр
финала живьём); SSE `seen` гасит точку во всех вкладках; записи без флага
(старые/импортированные) считаются просмотренными. Тот же паттерн — «урок готов»
(lesson-job). Это общий принцип: **у любого индикатора есть условие гашения**.

### 5.4 Ошибки и занятость

Занятая сессия → 409 `session is busy` на новый ход/смену модели/ext; archive во
время хода → 409; неизвестная модель → 400; ssh-провалы → 502 с хвостом stderr.
Общий try/catch роутера → 500 `{error}`.

## 6. Машины (ssh-клиенты) и работа на них

**Борда одна — серверов сколько хочешь.** Машина = запись в hosts.json с ssh-адресом.
Требование: **ключ на хосте** (`ssh-copy-id`) — BatchMode, пароли в headless не работают.
Все ssh-вызовы — `spawn('ssh', ['-o','BatchMode=yes','-o','ConnectTimeout=8',
'-o','StrictHostKeyChecking=accept-new', ('-p',port)?, addr, cmd])`, таймауты SIGKILL.
Экранирование аргументов в командах — одинарные кавычки с `'\''` (shq).

### 6.1 Проверка (⟳)

Один ssh-скрипт: `export PATH="$HOME/.local/node/bin:$PATH"` (неинтерактивный ssh
не читает .bashrc — PATH бутстрапа прокидываем сами) → `command -v node/git`,
`pi --version`. Результат — объект `check` в hosts.json: ok/hasNode/hasGit/hasPi/version.

### 6.2 Установка (⤓) — бутстрап без sudo

Shell-скрипт по ssh (7 мин таймаут): если node < 22.19 (минимум pi) или нет —
скачать тарбал `nodejs.org/dist/v<VER>/node-v<VER>-linux-<arch>.tar.xz` (arch:
x64/arm64/armv7l) в `~/.local/node`; `npm i -g @earendil-works/pi-coding-agent@latest`;
затем **синк кред**: локальные `~/.pi/agent/{auth,settings,models}.json` копируются
на хост (`printf '%s' <shq content> > ~/.pi/agent/<f>`) — тот же провайдер и ключ,
что у человека. Отдельная кнопка ⇆ — перезалить только креды (после ротации ключа).
Идея: клиент становится полноправной машиной исполнения за один клик.

### 6.3 Удалённые ходы и файлы

- Ход: run.sh деплоится на клиент (§4.2), запуск — одноразовый ssh + nohup
  (§4.3), артефакты — `~/.pi-board/`. Наблюдение — `ssh … tail -c +off -f`.
- Транскрипт/история — `ssh cat ~/.pi-board/sessions/<sid>.jsonl` (отсутствие
  файла — пустая история, не ошибка).
- Листинг папок на клиенте: `cd <dir> && pwd && ls -1Ap | grep '/$' | head -400`;
  `~/…` в путях разворачивается через кэшированный `$HOME` клиента.
- Удаление машины: каскад — стоп ходов её сессий, `rm -rf ~/.pi-board/{sessions,journal,pid}`,
  сессии хоста удаляются из registry.

### 6.4 Сайдбар: дерево машина → агент → сессия

«Агент» = рабочая папка: сессии группируются по `dir` внутри машины, сортировка по
`lastActivity`. У узла-агента на ховере `+` — создать сессию в этой папке; `+` у
машины — диалог выбора папки на ней. Статус-точки машины: ok (ssh+pi) / warn (ssh ок,
нет pi) / fail (недоступна).

## 7. Репозитории и зеркала: git-хаб машин

**Проблема:** код проектов надо раздавать на машины исполнения и забирать
результаты назад, а sshd на борде поднимать нельзя (машины не могут инициировать).

**Решение:** борда — git-хаб. Источник истины — origin каждого репо; борда держит
**bare-зеркала** в `data/mirrors/<name>.git` и раздаёт их. Весь транспорт инициирует
борда:

```
origin ──clone --mirror──> зеркало борды ──push --mirror (ssh)──> зеркало клиента
                                │                                        │
                     fetch board/* ←────────── push -f (локально) ←── рабочая папка
                                │                                        │
                                └── materialize: clone/checkout ──> рабочая папка
```

1. **add** `{name, origin}`: имя-slug `^[a-z0-9][a-z0-9_-]{0,63}$`, origin — абсолютный
   путь или URL → `git clone --mirror`.
2. **sync**: `git remote update --prune` из origin (ветки, defaultBranch через
   `symbolic-ref HEAD`).
3. **materialize** `{host?, dir, ref?}`: на борде — локально clone/update из зеркала;
   на клиенте — сначала `git init --bare ~/.pi-board/mirrors/<name>.git` (если нет) +
   `push --mirror` из зеркала борды (git-over-ssh через `GIT_SSH_COMMAND` с теми же
   опциями, remote URL — scp-style `user@host:~/…`), затем клиентский скрипт:
   нет папки → `clone -b`; есть → проверка `origin.url == ~/…/<зеркало>` (чужой
   origin → ошибка, не портим чужой чекаут) → `fetch --prune` → checkout →
   `merge --ff-only`; итог: `cloned|updated|diverged` + HEAD.
4. **collect** `{host?, dir, label?}`: HEAD рабочей папки → ветка `board/<label>`
   в зеркале (force, одноразовые ветки результатов). На клиенте: локальный push в
   клиентское зеркало, затем борда делает `fetch -f <клиентское зеркало>
   refs/heads/board/*:refs/heads/board/*`.
5. git-операции одного репо **сериализуются** in-flight множеством: повторный вызов
   → 409. Удаление репо — убрать из реестра и снести зеркало.

**Сессии × репо:** при создании сессии можно указать `{repo, ref}` — борда
автоматически материализует репо в `dir` (дефолт `~/pi-board-work/<name>` локально
и на клиенте). В шапке чата — `⎇ repo@branch`. Содержимое репо (правила AGENTS.md,
скиллы `.agents/skills/`) ездит внутри репо — борда агностична.

## 8. Debrief: допросить вернувшегося агента

Кнопка «⚖ debrief» на сессии, привязанной к репо. Идея: консолидация опыта —
**по правилам репозитория**, в котором работала сессия, а не по правилам борды.

1. Снять транскрипт (локально/`ssh cat`), отрендерить в markdown
   (`## 👤 user / ## 🤖 assistant / ### ⚙ tool ✓✗`, обрезки по 4000/1200 симв.) →
   `data/debrief/<sid>-transcript.md`.
2. Идемпотентно материализовать рабочую копию репо на борде
   (`~/pi-board-work/<name>`).
3. Создать **локальную** сессию-дебриф в этой папке (`debrief·<title>`, `ext:false` —
   сервисная) с промптом: «прочитай транскрипт; изучи правила ЭТОГО репозитория
   (AGENTS.md, docs/, candidate inbox — что найдёшь); проведи консолидацию ПО
   ПРАВИЛАМ РЕПОЗИТОРИЯ; нет правил — markdown-отчёт хорошо/плохо/сохранить/предложения;
   каждый вывод — из транскрипта, „устойчивого урока нет“ — валидный результат;
   созданные файлы закоммить (git -c user.name=board-debrief …)».
4. Дальше сессию-дебриф допрашивают интерактивно; карточка дебрифа видна на
   странице знаний (§19) и ведёт на сессию.

## 9. Коллаб: канбан задач и форум агентов

Координация нескольких агентов и людей поверх борды. Отдельная вкладка `/board`
(канбан + форум, живые обновления SSE). Данные — `data/board.json` и
`data/forum.json`. API рассчитан на **curl из агентов** (в т.ч. с удалённых машин
по LAN-адресу).

### 9.1 Канбан

```
{seq, tasks: [{id(8hex), n(№ при создании), title(≤200, обязателен), body(≤4000),
  plan(путь plans/…, ≤300), author(≤60, дефолт anon),
  status: open|progress|review|done, createdAt, movedAt, updatedAt}]}
```

- Создание `POST /api/board`, правка/смена статуса `POST /api/board/:id`
  `{status?|title?|body?|plan?|author?}` (невалидный статус → 400), удаление DELETE.
- Карточки таскаются drag&drop или кнопками ◀ ▶; статусные переходы свободные.
- Число незакрытых задач — бейдж кнопки ▦ на главной и точка `●` в title вкладки.
- **Задача-план** (конвенция CC): в `plan` лежит путь markdown-файла плана;
  клик по карточке открывает план целиком с markdown-рендером, план можно править
  прямо из борды (§9.4).

### 9.2 План следует за статусом (relocatePlan)

Жизненный цикл файла плана синхронизирован со статусом задачи — карточка всегда
показывает живой путь:

- перенос в **done**: `plans/active/<name>.md` → `plans/executed/<YYYY-MM-DD>-<name>.md`
  (коллизия → суффикс -2, -3…); файла нет — ищем в executed/ по имени/без
  дата-префикса и «чиним» путь (агент мог перенести файл сам); путь в задаче обновляется.
- возврат в работу: `executed/<дата>-<name>.md` → `active/<name>.md`
  (дата-префикс снимается).
- мусорное поле плана (не plans/…, не .md) не трогается. Ошибки → тихо, путь как был.

### 9.3 Форум

`{seq, messages: [{id, n, topic(латиница-слаг ≤24, дефолт general), author, text(≤2000), at}]}`
Темы фиксированы смыслом: `general`, `sync`, `ports` (анонсы занятых портов/веток —
общие ресурсы), `board`. Capped-журнал: 1000 сообщений, при превышении хвост
обрезается до 800 (гистерезис, чтобы не переписывать файл на каждом сообщении).
GET `?topic=&limit=` (хвост, clamp 10..500), POST, DELETE только своё
(`?author=`; 403 при несовпадении; без author — может кто угодно).

### 9.4 API планов (файлы в репо борды)

`GET /api/plan?path=…` / `POST /api/plan {path, content}` — только `plans/**.md`
(path-безопасность: префикс plans/, только .md, длина ≤300, канонизация не выпадает
из корня; иначе 400), запись атомарная (≤512 KB), `mkdir -p` на пути. SSE
`plan_changed {path}` — открытые вкладки перечитывают.

### 9.5 Коллаб-хинт в каждый ход

Блок `<collab>…</collab>` инъецируется в `--append-system-prompt` каждого хода
(вместе с библиотекой, §4.4). Содержимое:

1. Адрес борды и author (sid сессии) для curl; ссылка на человеческую доску `/board`.
2. **Императивное правило**: «заметная работа = задача в канбане, общий ресурс =
   анонс в ports»; при done «борда сама переносит план в executed — файл не переноси
   руками»; обязательный статус done по завершении.
3. Готовые curl-примеры с подставленным author.
4. **Живое состояние доски**, перечитываемое с диска на каждый ход: сколько задач
   открыто + до 5 незакрытых задач этого агента (`#n [status] title`) — агент видит
   их каждый ход, а не один раз; «твоих задач нет — если текущая работа заметная,
   создай задачу сейчас».

Выключение: `PI_BOARD_COLLAB_HINT=0`. Удалённым сессиям — только при не-loopback
борде (иначе агент будет ломиться в недоступный адрес).

## 10. Experience library — библиотека уроков

**Идея (порт harnessing-рекурсии из Harness²):** по каждой рабочей папке (домену)
копятся уроки `{cue, lesson, evidence}` и автоматически инъецируются в системный
промпт каждого хода этого домена. Цикл: сессия → extract (черновик) → человек
правит → урок в домен → все следующие ходы домена его видят.

### 10.1 Домен

`domainSlug = slugify(basename(dir)) + '-' + sha1((host||'local') + '|' + dir).slice(0,6)`
— читаемо и без коллизий между машинами; `~` → база `home`; slugify: lowercase,
NFKD, не-[a-z0-9] → `-`, cap 40. Формат: `^[a-z0-9][a-z0-9_-]{0,80}$`.

### 10.2 Данные

```
data/library/<domain>/
  INDEX.md                      генерируемый индекс (руками не править)
  entries/<id>/meta.json        источник истины
                /EXPERIENCE.md  человекочитаемый рендер
```

- id записи: `<YYYYMMDD>-<HHmmss>-<hex4>`; **meta.json**: `{id, domain, cue, lesson,
  evidence, sessionId?, dir?, createdAt}` — все три текстовых поля непустые
  (инвариант валидности, порт `has_experience`; запись без поля отбрасывается).
- INDEX.md пересобирается из записей после каждой мутации (по возрастанию даты).

### 10.3 Инъекция

`renderMemoryBlock(domain)`: нет записей → null (блока нет). Иначе — полный текст
уроков, **свежие первыми**, суммарно ≤ 8000 символов (первый не влезающий обрывает
перебор; если даже первый не влезает — жёсткая обрезка полей cue≤200/lesson≤7400/
evidence≤300). Заголовок: `# Experience library (shown/total lessons)` + инструкция
«применяй релевантные, игнорируй нерелевантные» + отсылка к INDEX.md при усечении.
Идёт в `--append-system-prompt` (хвост системного промпта — кэш цел).

### 10.4 Extract (человек в цикле)

Кнопка «✎ урок из этой сессии»: `POST /api/library/<domain>/extract {sessionId}` —
только локальная сессия (ssh → 400), не running (409), иначе 202 + jobId. Фоновая
задача = один pi-вызов: системный промпт «предложи черновик урока; ответ ТОЛЬКО JSON
`{"cue","lesson","evidence"}` или `{"skip":"причина"}`» + сжатый транскрипт
(40 сообщений / 30 KB: `[user]/[assistant]/[tool:name] …` по 1500 симв. на строку).
JSON вырезается подстрокой от первого `{` до последнего `}`. Черновик **эфемерен**
(память процесса, рестарт сбрасывает кнопку); человек правит → POST entries →
запись на диск + SSE `library_changed`. Один активный job на сессию, ≤ 3 concurrently,
кэш job'ов ≤ 40. UI-уведомление SSE `lesson {phase:ready|failed}` + опрос-страховка.

Отказ: битый JSON → job error (≤300 симв.), пустой → skip; ошибка инъекции в ходе →
null, ход без блока; `PI_BOARD_LIBRARY=0` — выключить.

## 11. Долговременная память: ребёнок recall/persist

**Идея (порт memory-subagent из coddy):** на каждое сообщение пользователя в фоне
стартует ещё один headless pi-«ребёнок», запертый на двух корнях Obsidian-заметок.
Один запуск = один режим:

- **RECALL** (по умолчанию): найти в заметках факты, полезные для ЭТОГО сообщения.
  Финал строго `Already on disk:\n- факт` (до ~10 фактов, «факты, не указатели» —
  без путей/имён файлов) или ровно `(no memory hits)`. Метод: grep по словам
  сообщения и тегам в обоих корнях → прочитать хиты → пройти `[[вики-ссылки]]` ≤ 2
  шагов; пусто — английские ключевые слова, find.
- **PERSIST** (только явная просьба «запомни/сохрани/забудь»): сначала найти похожую
  (слова/теги/ссылки) → обновить, дубль не создавать; иначе новая заметка. Оп-аут
  «не ищи в заметках» → короткая строка без инструментов.

### 11.1 Корни заметок

- **project**: `<рабочая папка сессии>/.pi-board/memory/` — коммитится в проект;
- **global**: локально `<борда>/data/memory/`, на ssh-клиенте `~/.pi-board/memory/`.

Формат: `.md` + frontmatter `{title, type: term|decision|fact|preference, tags[],
created, updated}`, тело ≤ 900 символов (атомарные единицы, длинные темы дробятся
и связываются `[[ссылками]]`), имя файла = слаг заголовка. Инварианты: секреты не
хранятся; удаление/переименование только по явной просьбе. Оба корня — готовые
Obsidian-vault'ы: человек правит заметки руками наравне с ребёнком.

### 11.2 Механика

Роль (системный промпт ребёнка): «ты — ребёнок долговременной памяти; дано ОДНО
сообщение, отвечать пользователю запрещено, финальный текст читает только сервер;
инструменты — только к двум корням». Запуск: `pi -p --mode json --no-extensions
--no-mcp --no-skills --no-context-files --no-session --tools read,bash,write,edit
--append-system-prompt <роль> [--model $PI_BOARD_MEMORY_MODEL] -- <задача>`;
задача = пути корней + сообщение (≤16 KB). Локально — spawn в `s.dir`, удалённо —
тот же argv по ssh. Финал = последний `message_end` ассистента.

Фазы результата: `delivered` (отчёт ≤800 симв., обрезка с маркером), `none`
(no memory hits), `late` (не успел за WAIT — ход идёт без блока, ребёнок
дорабатывает: PERSIST-эффекты ценны), `failed` (упал — никогда не ошибка хода),
`skipped` (уже работает один на сессию; ≤3 concurrently на борду).

### 11.3 Вставка в ход (turn_context)

Отчёт вклеивается **в текст сообщения** (хвост истории, не системный промпта — кэш цел):

```
<оригинальный текст>

<turn_context name="memory">
Память из заметок прошлых сессий (recall; факты, применять по релевантности):
<report>
</turn_context>
```

Чип 🧠 в шапке чата показывает фазу (…/✓/∅/✗/поздно). Пробы refine ребёнка не
запускают. Env: `PI_BOARD_MEMORY=0|_WAIT(120s)|_TIMEOUT(150s)|_MODEL|_DEBUG`.

### 11.4 Разница library × memory (важно не смешивать)

| | library | memory |
|---|---|---|
| Слой | системный промпт (до хода) | текст хода (turn_context) |
| Структура | домены → дисциплинированные entries | свободные Obsidian-заметки |
| Кто пишет | человек через API после extract | pi-ребёнок по просьбе в чате |
| Триггер | всегда для домена | каждое сообщение (recall) / явное (persist) |

## 12. Refine: Propose–Probe–Compose

**Идея (порт Propose–Probe–Compose из Harness²):** для последнего запроса сессии
подобрать улучшение «гарнеса» (среды агента) слепым A/B-тестом. Судья — человек.

1. **Propose**: один pi-вызов (proposer) по последнему user-запросу + фокусу +
   хвосту истории → **ТОЛЬКО JSON** `{"variants":[…]}`; вариантов k−1 (k clamp 2..3),
   k-й кандидат — всегда **базовая конфигурация**. Вариант — только дельты от базы
   («omitted-is-inherited»): `appendSystemPrompt` (≤4000), `skills[]` (пути ≤300),
   `tools` (allowlist-строка ≤200), `name` (≤60); неизвестные ключи → отказ.
   Невалидный вывод → 1 ретрай → fallback-вариант («сформулируй план в 3 пунктах и
   проверь результат»).
2. **Probe**: параллельные **эфемерные** сессии `probe-<gid>-<A|B|C>` — обычные ходы
   через тот же ledger-раннер (startTurnEx с доп. параметрами), но **не в registry**
   и не в сайдбаре; всегда локальные, `ext:false`. Стрим каждой — в колонку модалки.
   **Анонимность**: метки A/B/C назначаются случайной перестановкой кандидатов
   (Fisher–Yates, crypto); маппинг `labelMap` живёт в `data/probe/<gid>/meta.json`
   и **не покидает сервер** до выбора — judge выбирает вслепую.
3. **Compose (adopt)**: человек выбирает метку (все пробы должны быть done) →
   маппинг раскрывается; принятый вариант + причина становятся **уроком в библиотеке
   домена** (harnessing-цикл замкнулся: cue=задача, lesson=«принятый вариант: …»,
   evidence=почему выбрано); снапшот — `data/probe/<gid>/harness.json`.

Состояние пробы не хранится, а **выводится** из файлов: running по running-карте;
assistant-сообщение в истории → done; `board_exit` из журнала ∉ {null,0,130,143} →
failed; иначе idle. Рестарт борды во время проб → группы `orphaned` (пробы не в
registry, обычный recovery их не знает — отдельный скан при старте). Cancel убивает
пробы; DELETE группы чистит файлы проб. Отладка без затрат: `PI_BIN=tests/fake-pi.sh`.

## 13. Сабагенты и ext-сессии

**Расширения pi в ходах включены по умолчанию** (решение пользователя; раньше —
выключены): прежде всего это инструмент `subagent` (пакет pi-subagents) — агент
сессии делегирует фоновую работу async-детьм (scout/worker/reviewer), не блокируясь.

- Флаг **ext** у сессии: `true` по умолчанию; чекбокс «ext» в шапке чата / `POST
  /api/sessions/:id/ext {ext:bool}` / `POST /api/sessions {ext:true}`; 409 во время
  хода. `PI_BOARD_EXTENSIONS=0` — жёстко всем. Служебные ходы (пробы refine, debrief,
  ребёнок памяти) — всегда `ext:false`.
- **Кап детей**: `PI_SUBAGENT_MAX_SPAWNS_PER_SESSION=12` в env хода (только ext-ходы;
  своё окружение может перебить).
- **Гайд** `<subagents>` инъецируется в ход: делегируй async-детьми, не жди bg_wait —
  уведомление придёт само, **ход дожидается детей на agent_end (auto-drain ≤30 мин)**,
  финальный ответ уже со сводкой результатов; timeoutMs ≤ 600000; ребёнок не видит
  контекст родителя — в task цель/файлы/критерий/формат отчёта.
- **Наблюдение**: события `tool_execution_start/end` с `toolName:"subagent"` →
  SSE-карточки `▸ subagent: <agent> <task>` (старт) и `фон · run <id>` (receipt);
  реальный итог ребёнка приходит обычным tool_result. Стоп хода убивает родительский
  pi; дети в отдельном runner-процессе переживают — статусы видны следующему ходу.

## 14. Пассивная диагностика хода

Идея: pi стримит в журнал больше, чем нужно для чата — стоп-причины, ретраи,
компакции, usage. Всё это собирается **пассивно** по ходу (`diag` в состоянии хода)
и отдаётся в `done`-событии: `notice` (человекочитаемо: «ответ обрезан лимитом
вывода», «pi ретраил ×2», «компакция 146.5k→31.2k tok», «похоже на зацикливание»),
`stopReason`, `retries`, `compacted`, `loop`.

- **usage-агрегаты**: токены/стоимость копятся по сессии (`usage` в registry:
  `{tokens, cost, turns}`), включая usage суммаризатора компакции; видны в карточке.
- **Обрезанный ответ** (`stopReason=length`): баннер «⚠ Ответ обрезан» с кнопкой
  «Продолжить» — отправляет сообщение-надж следующим ходом; баннер переживает
  перезагрузку (стоп-причина читается из registry).
- **Loop-scan пост-фактум** (порт streamRepeatDetector из coddy): застрявшая в цикле
  модель эмитит периодический хвост. Храним хвосты текста/мышления за ход (64 K
  симв.); на финале ищем **минимальный период** p ∈ [12, 512] символов, повторённый
  ≥5 раз подряд, с ≥4 разными рунами в юните (чтобы `-----` и разделители таблиц не
  считались циклом). Нормализация: lowercase, схлопывание пробелов; окно 4096.
  Трип → notice + `diag.loop`. Выключить: `PI_BOARD_LOOP_GUARD=off`.

Итог хода (`lastTurnEnd.state`): агент ответил → `done`; остановлен/aborted →
`stopped`; процесс упал → `error` (+error-текст).

## 15. Self-reload: борда чинит сама себя

**Идея:** сессии работают над репозиторием самой борды; фикс применяется к живой
копии — и борда немедленно перезапускается на месте. Перезапуск дёшев, потому что
ходы detached (ledger), registry на диске, SSE-клиенты ловят событие и обновляются.

### 15.1 Супервизор (scripts/serve.sh, `npm start`)

Рестарт-цикл: `node server.js 2>>reload/stderr.log` → wait. Коды выхода:

- **75 (EX_TEMPFAIL)** — сервер сам попросил перезапуск → поднять снова;
- **0** (Ctrl+C/SIGTERM) — остановиться;
- прочие — падение: если «в полёте» reload (есть `pending/manifest.json` +
  `known-good/manifest.json`) и откат ещё не делался → запустить rollback.js и
  стартовать снова; **повторное падение после отката — стоп** (без зацикливания);
  крах вне reload-цикла — показать хвост stderr и остановиться.

Супервизор экспортирует `PI_BOARD_SUPERVISOR=1` (без него `POST /api/reload` — 409)
и согласованный `PI_BOARD_DATA`.

### 15.2 API reload

- `POST /api/reload` — перезапустить как есть (правки уже на диске);
- `POST /api/reload {branch}` — применить ветку `board/<label>` (результат collect,
  §7): fetch из своего зеркала + `merge --no-edit` в живую копию; конфликт → 400 +
  `merge --abort`, рестарт не начинается. Для этого репо борды регистрируется в ней
  самой как обычный репо (origin = папка борды).
- **Guard перед рестартом**: все корневые `*.js` проходят `node --check` — сломанный
  синтаксис не уронит борду (400, рестарт не начинается).
- `GET /api/reload` — состояние (git живой копии, board/*-ветки, pending);
  `GET /api/health` — `{ok, startedAt(поколение), supervisor}`.
- Перезапуск: broadcast `reload` → разорвать SSE-клиенты (пойдут на реконнект) →
  `process.exit(75)`.

### 15.3 Known-good снапшот и авто-откат

- Поколение, прожив `PI_BOARD_RELOAD_STABLE_MS` (10 с), снимает **known-good**
  снапшот: все корневые `*.js` + package.json + run.sh + public/ + scripts/ →
  `data/reload/known-good/files/` + `manifest.json` (атомарно tmp+rename).
- `POST /api/reload` перед выходом пишет маркер «reload в полёте»:
  `data/reload/pending/manifest.json` `{at, reason, branch, preHead(HEAD до merge)}`.
- Если новое поколение упало на подъёме — супервизор запускает **rollback.js**
  (сам откатчик берётся из known-good снапшота — лежащий на диске может быть
  сломан правкой): `git reset --keep preHead` (убрать merge-коммит; до возврата
  файлов — `--keep` отказывает на отличающихся) → вернуть каждый файл из
  known-good (только отличающиеся) → удалить новые `*.js`, отсутствующие в
  снапшоте → хвост stderr (16 KB) в `last-crash.txt` → маркировка
  `rolledBack:true, changed:bool`.
- **Rollback-отчёт**: поднявшееся после отката поколение рассылает сессиям, правившим
  борду (dir = папка борды или материализованная копия её репо; до 3 самых свежих),
  ход с текстом ошибки упавшего поколения — агент видит, чем упало, и чинит.
  Не шлётся, если код не менялся (падение не из-за правок, напр. занят порт) или
  `PI_BOARD_CRASH_REPORT=0`.
- UI: SSE `reload` → тост; поллинг `/api/health` 500 мс, пока `startedAt` не
  сменился → `location.reload()` (90 с таймаут — «посмотри терминал»).

## 16. Общие сессии с консолью и board-parity

**Общий файл.** Консольные pi-сессии (`~/.pi/agent/sessions/…`) показываются
группой в сайдбаре (read-only превью: cwd из первой строки, title из первого
user-запроса, head 64 KB). Кнопка «⤵ продолжить» связывает оригинальный файл с
сессией борды (`extFile`) — **без копии**:

- ходы борды пишут прямо в файл консоли; `pi -c`/`pi -r` в том же cwd видит их же
  (живого хвоста в открытом TUI нет — перечитывает при открытии/resume);
- **кооперативная блокировка**: перед ходом борда проверяет «тишину» файла — если
  TUI писал < 15 с назад, ход отклоняется (409 «консоль активна»); жёстких
  блокировок у pi нет — контракт вежливости;
- живой вид TUI → борда: `fs.watchFile` (поллинг 3 с) на прирост сообщений → SSE
  `ext {messages}` (доклейки в чат без перезагрузки); ротация/усечение — просто
  догоняем;
- удаление связанной сессии оригинал **не трогает** (только артефакты борды);
  `{"copy":true}` — старый режим развилки-копии.

**board-parity** (расширение pi в `.pi/extensions/` репозитория борды): консольные
pi-сессии в корне проекта живут по правилам ходов борды — то же поведение инъекций
(библиотека + коллаб-хинт в appendSystemPrompt) и ребёнок памяти (тот же
turn_context). Ключи: не активируется в процессах ходов борды (маркер
`PI_BOARD_EXTENSIONS=1` в env хода — блоки уже вставил сервер, дубль не нужен);
живость борды проверяет TCP-пробой порта (мёртвой не рекламируем); любые отказы —
молча. Идея: **одни и те же знания/память у консоли и у борды**.

## 18. Совместимый слой для чужого UI (compat)

**Идея:** вендорнутый web-UI от coddy-agent (`web-ui/dist`, отдаётся на `/ui`)
разговаривает с бэкендом на своём протоколе — и борда говорит на нём же, **не трогая

(`ready`/`turn_started`/`turn_ended`, ретроспективные turn_started для идущих),

передаётся в startTurn — фреймы coddy-формата пишутся прямо в ответ.

## 19. UI: принципы и структура

Три страницы, vanilla JS без сборки: `/` (index.html — сессии + чат), `/board`
(канбан + форум), `/knowledge` (уроки + заметки + дебрифы единой лентой). Общие:
палитра-тёмная тема на CSS-переменных, `api()` → fetch+JSON (ошибка = throw),
SSE-клиент, тосты, ago().

### 19.1 Принципы (инварианты)

1. **DOM-безопасность**: любые пользовательские/модельные строки — только
   `createElement`/`textContent`; innerHTML запрещён для данных (модалки, чат,
   канбан, знания). Поймано ретро как XSS-вектор — теперь контракт тестов.
2. **Один SSE на страницу** (`/api/events`), поллинг — только страховка (сессии 5 с,
   refine 2 с, lesson-jobs 4 с, заметки 60 с) + кэши (pi-сессии 60 с, архив 30 с).
3. **Race-защита асинхронности**: после каждого `await` — проверка актуальности
   (`cur.id`, id задачи модалки, jobId); uiConfirm — см. ниже.
4. **Идемпотентные ре-рендеры**: сайдбар/доска перерисовываются целиком из state;
   чипы — Map по id + `isConnected`.
5. **Seen-семантика** у всего «непросмотренного» (ход, урок) — §5.3.
6. **Модалки** — нативные `<dialog>`+`showModal`; uiConfirm (замена confirm):
   Promise-обёртка; повторный вызов при открытом окне резолвит предыдущий в false;
   флаг собственного закрытия (cmSelfClose) — close-событие диалога ставится в
   очередь асинхронно, без флага Esc одного окна ложно отменил бы следующий диалог;
   фокус на «отмене» (случайный Enter не подтвердит удаление).
7. **Стрим — plain, финал — markdown**: дельты текстом (дёшево), при финале
   перерисовка разметкой (общий md.js).

### 19.2 Главный экран

- Сайдбар: дерево машина → агент(папка) → сессии (§6.4) + спецгруппы «консоль pi»
  и «архив»; статус-точки машин (§6.1) и сессий (`live` пульс при running;
  непросмотренное завершение — done/warn/fail по seen); на карточке — preview,
  токены/цена, ⚠ обрезан.
- Чат: `.msg.user`/`.msg.assistant` + чипы `<details>`: ⚡ tool (args → result),
  💭 мышление (свёрнуто), ▸ subagent; стрим с курсором; автоскролл только если
  nearBottom (<90 px), force-прыжок без smooth-анимации.
- Шапка чата: чип 🧠 памяти, селектор модели, чекбокс ext, «⇄ общий файл · ⎇ repo@ref ·
  ⇄ host · dir», кнопки ⚖ debrief (если репо), ³ refine (локальные), ▤ lib (уроки домена).
- Композер: Enter отправка / Shift+Enter перенос, автовахта textarea; busy → кнопка
  ■ stop. Баннер обрезания + «Продолжить».
- Модалки: hosts (CRUD машин + ⟳/⤓/⇆), dir-браузер (GET /api/fs, home/вверх/mkdir/
  rename + пара селектов репо·ветка → материализация при создании), lib/lesson
  (уроки: генерация черновика фоновая, кнопка «урок готов»), refine (колонки проб),
  reload (⟳), h2 (прогоны harness2).

### 19.3 md.js — безопасный markdown

UMD (`module.exports` для Node-тестов, `root.Md` в браузере): `Md.parse(text)` —
чистая функция в дерево блоков; `Md.render(el, text)` — DOM только из
createElement/textContent; `Md.safeHref` — схемы только `https?:|mailto:`,
протоколо-относительные `//` — нет; небезопасная ссылка остаётся **буквальным
текстом**. Поддержка: заголовки, фенсы с data-lang, инлайн-код, bold/italic/strike,
ссылки (target=_blank + noopener), автоссылки, картинки (только http(s), lazy,
no-referrer), списки ul/ol вложенные, цитаты, hr, GFM-таблицы с выравниванием,
бэксплейсы. Используется чатом и канбаном (планы).

## 21. Процесс разработки: планы, ретро, уроки

Разработка самой борды шла фазами по планам — и этот процесс часть концепции:

- **Планы** живут в `plans/active/<name>.md` (файлы-планы CC-стиля: контекст, фазы,
  проверки-чеки, DoD); выполненные архивируются в `plans/executed/<дата>-<name>.md`
  (борда делает это сама при переносе задачи в done, §9.2); aborted — отдельно.
- **Ретро** на границах фаз (вендоренный скилл retro): поиск кандидатов улучшения
  среды (навигация, guardrail'ы, стандарты кодинга, tool economy, no-op'ы в
  инструкциях) → решения пользователя → применение. Ретро-файлы в plans/executed/retros/.
- **Уроки** из ретро идут в experience library домена (§10) — замкнутый цикл.
- **Заметная работа = задача в канбане** (§9) — параллельные сессии координируются
  доской и форумом (тема ports для общих ресурсов).
- Практики, родившиеся так: карта файла server.js в шапке; сверка `git status &&
  git log` перед стартом фазы (параллельные сессии могли переставить структуру);
  в планах ссылки на имена функций, не номера строк; индикатор без условия гашения —
  не сигнал; свежий UI ≠ свежий сервер (curl-ни новый роут на живом порту).

## 23. Порядок воссоздания

Если строить с нуля, порядок зависимости примерно такой (каждый шаг — работающий
продукт):

1. **MVP-борда**: HTTP+SSE, реестр сессий, запуск `pi -p --mode json --session`
   синхронно/спавном, чтение истории из jsonl, минимальный чат (стрим текста).
2. **Ledger**: run.sh + journal/pid/sentinel, tail-наблюдение с offset, стоп,
   recovery при старте. Теперь ходы переживают всё.
3. **SSH-машины**: hosts.json, check/install/sync, удалённый запуск через
   nohup+ssh, дерево сайдбара, удалённый fs-браузер.
4. **Репо и зеркала**: add/sync/materialize/collect, привязка сессий к репо,
   дефолтная рабочая папка.
5. **Self-reload**: serve.sh (код 75), /api/reload, known-good, rollback.js,
   rollback-отчёты. Зарегистрировать репо борды в самой борде.
6. **Диагностика**: diag-сбор из журнала, notice, usage-агрегаты, баннер обрезания,
   loopguard.
7. **Experience library**: домены, entries, инъекция в append, extract-флоу,
   страница знаний (позже).
8. **Коллаб**: board.json/forum.json, канбан+форум вкладка, план-следует-за-статусом,
   /api/plan, коллаб-хинт в ходы.
9. **Память**: ребёнок recall/persist, корни заметок, turn_context, чип.
10. **Общие консольные сессии** (extFile) + **выбор модели** + **архив** + **debrief**.
11. **Сабагенты**: ext-флаг по умолчанию, кап, гайд, SSE-карточки; автонаименование
    сессий (piOneShot).
12. **Refine (PPC)** и, опционально, **compat-слой** под готовый UI и **harness2**
    (если нужна исследовательская надстройка).
13. **Тесты** — сопровождают каждый шаг: fake-pi сразу после шага 1, with-board.sh
    после шага 3, check.sh — guardrail с первого дня.

Ключ к успеху — держать инварианты раздела 4 (файлы как истина) и 19.1
(DOM-безопасность, SSE-центричность, seen-семантика): остальное — композиция.
